**Rule enforced in every prompt:** a file inside `features/X` may import from `core/` freely, but may **never** import from `features/Y/data` or `features/Y/presentation` directly. Cross-feature communication happens only through: (a) shared entities promoted to `core/` if truly shared (e.g. a `TourSummary` shown on both Explore and Search), or (b) navigation via `go_router`, or (c) Riverpod providers explicitly exposed for that purpose. This is what keeps the app modular and prevents circular dependencies as it grows.

**Layer discipline (KISS applied deliberately):**
- Simple, mostly-CRUD features (`explore`, `search`, `tour_details`, `profile`, `concierge`, `notifications`) use **two** layers: `data` (repository implementation + Firestore mappers) and `presentation` (screens/widgets/controllers calling the repository directly). No separate `domain` use-case classes — the repository interface itself is the domain boundary.
- Features with genuine multi-step business logic (`booking` — price calculation across nights/participants/private-vehicle surcharge; `checkout` — PaymentIntent creation → Stripe confirmation → Firestore booking write, which must be atomic and handle partial failure; `reviews` — photo upload + Firestore write + loyalty point increment, which must be sequenced) use a `domain/usecases/` folder with one class per discrete operation, each with a single `call()` method. This is the only place use-case classes are allowed — don't add them elsewhere "for consistency," that would violate KISS.

### 3.3 Spacing, radius, elevation, shape

```
spacing:  base 8 / xs 4 / sm 12 / md 16 / lg 24 / xl 32 / containerMargin 20 / gutter 16
radius:   sm 4 / default 8 / md 12 / lg 16 / xl 24 / full 9999  (px)
```
- Buttons, input fields, small components → `radius.default` (8px).
- Premium containers — tour cards, feature blocks, the dark "What's Next" panel — → `radius.lg` (16px).
- Cards use `lg` (24px) internal padding.
- Sections are separated by `xl` (32px) vertical gaps minimum.
- Elevation: Level 1 = flat/background, no shadow. Level 2 (cards) = `BoxShadow(color: Color(0x0D002349), blurRadius: 20, offset: Offset(0,4))` (navy-tinted 5%-opacity shadow per design doc). Level 3 (floating actions, modals, the payment-processing overlay) = larger blur radius (~32) and higher opacity (~10%), same navy tint.
- Icons: 24px bounding box, 2px stroke, linear style (Material Symbols Outlined). Where the source shows a duotone accent (e.g. gold highlight inside an icon), implement with a `Stack` of two icon layers rather than a custom icon font.

### 3.4 Core shared components to build once (Prompt 2), reused everywhere

- `PrimaryButton` — navy fill, white label, full-width by default, pill or 8px-radius per call site, loading spinner state, disabled state at 38% opacity.
- `SecondaryButton` — outlined navy border, navy text, white fill.
- `GoldAccentButton` — for "Book Now"/"Claim"/flash-deal CTAs only.
- `AppTextField` — rounded 8px, grey `surfaceContainer` fill when unfocused, navy border glow when focused, leading icon slot, error text slot.
- `AppCard` — white surface, `lg` radius, Level 2 shadow, `lg` padding.
- `AppChip` — grey background/navy text inactive, navy background/white text active (categories, filters).
- `RatingStars` — read-only display variant (gold filled stars) and interactive input variant (tap to rate, used in Reviews).
- `SectionHeader` — title + optional "See All" trailing action, used on Explore (Featured Tours, Popular Destinations).
- `LoadingIndicator`, `EmptyStateView`, `ErrorStateView` — every screen that loads from Firestore must use these three for their respective states; never leave a screen with an unhandled spinner-forever or blank-screen-on-error.

## 4. Canonical Information Architecture (resolves the 4 conflicting bottom-nav variants in the source export)

**Bottom navigation — exactly 5 tabs, in this order, persistent across the app via `StatefulShellRoute.indexedStack`:**

1. **Explore** (icon: compass) — Home/dashboard screen.
2. **Search** (icon: magnifying glass) — Search & filters entry point.
3. **Trips** (icon: ticket/ID card) — segmented into **Upcoming / History / Saved**, matching `luxetravel_profile_dashboard.png`. This is where the corrupted `saved_tours.png` and `profile_history.png` screens live, as the History and Saved segments.
4. **Concierge** (icon: chat/headset) — Travel Concierge chat.

The active tab uses the navy filled-circle treatment shown in `luxetravel_search_filter.png` and `luxetravel_booking_confirmation.png` (active icon in a navy or gold circular background depending on the specific tab's accent — use navy as default, gold is reserved for promotional emphasis only, do not use gold for nav selection state to avoid diluting its "premium" meaning elsewhere).

**Security rules requirement (build in Prompt 1/14):** users can only read/write their own `users/{uid}` subtree, `bookings` where `userId == request.auth.uid`, and only Cloud Functions (admin SDK, bypassing rules) can write `status`, `stripePaymentIntentId`, `bookingReferenceCode`, and `reviewed` on a booking — the client may only *create* a booking in `pending` state and never self-promote it to `confirmed`. `tours` and `tours/*/reviews` are public-read, authenticated-write (reviews only, and only by the booking's owner after `status == completed`).

## 7. Engineering conventions (enforced in every prompt, not just Prompt 1)

- Lint with `flutter_lints` plus these additions in `analysis_options.yaml`: `always_declare_return_types`, `avoid_print` (use a `Logger` wrapper instead), `prefer_const_constructors`, `prefer_final_locals`, `unawaited_futures`, `avoid_dynamic_calls`.
- No widget file exceeds ~250 lines; if a screen grows past that, extract sub-widgets into the screen's `widgets/` folder — this is the practical KISS/SRP threshold to enforce, not a hard rule but a trigger to stop and refactor.
- Every public Riverpod provider/controller has a doc comment stating its single responsibility in one sentence. If you can't state it in one sentence, it's doing too much — split it.
- No screen calls Firestore/Storage/Stripe SDK methods directly. All access goes through a repository in that feature's `data/` layer.
- All user-facing copy strings live in `core/constants/app_strings.dart`, organized by feature as nested classes (e.g. `AppStrings.auth.signInButton`), so copy review/localization later is a single-file change.
- Every async screen has 4 states handled explicitly: loading, empty, error, and loaded-with-data. Use Riverpod's `AsyncValue.when(...)` to force this at the call site.
- Commit after each numbered prompt in `02_BUILD_PROMPTS.md` is completed and its acceptance checklist passes, with a message matching the prompt's feature name (e.g. `feat(auth): login/register screens with Firebase Auth`).
